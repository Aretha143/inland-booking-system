# Inland Multi Cuisine & Stay — Booking Confirmation System

Internal hotel booking management and confirmation system for **Inland Multi Cuisine & Stay**, Budhanilkantha, Kathmandu, Nepal.

Bookings are taken by staff over Instagram, Facebook, WhatsApp, phone or at the desk, entered here, and confirmed to the guest with a professional email sent **from the hotel's own Gmail account through the Gmail API** (OAuth 2.0 — no passwords, no SMTP).

## 1. Project overview

| | |
|---|---|
| **Frontend** | Static HTML/CSS/JavaScript (ES modules, no build step) hosted on **GitHub Pages** |
| **Database / Auth** | **Supabase** (PostgreSQL + Auth + Row Level Security) |

| **Email** | **Gmail API** `users.messages.send` with OAuth 2.0 refresh token |
| **Secrets** | Supabase Edge Function secrets + Supabase **Vault** (refresh token, encrypted at rest) |

Features: dashboard, bookings list with search/filters, booking form with availability check, **day-use (daycation) bookings**, booking details with full email history, room availability calendar, room management, check-in / check-out, cancel, printable confirmation, staff management, admin settings, Gmail connection panel with test email, and email logs.

### What is *not* in the repository (by design)

Never committed, never in frontend code: Google client secret, Google refresh/access tokens, Supabase service-role or secret keys, database password, Gmail password, `.env` files, service-account JSON.

Only the **Supabase project URL** and **publishable (anon) key** appear in `assets/js/config.js` — these are designed to be public and are useless without a valid login because every table is protected by Row Level Security.

## 2. Architecture

```
GitHub Pages (static frontend)
        │  supabase-js (publishable key + user session)
        ▼
Supabase Auth ──► profiles (ADMIN / STAFF)
        │
        ▼
Supabase PostgreSQL  ← Row Level Security on every table
        │
        ▼
Supabase Edge Functions (service role, server-side only)
   • gmail-oauth                 • send-booking-confirmation      • admin-users
        │
        ▼
Google OAuth 2.0  ──►  Gmail API  ──►  hotel Gmail  ──►  guest inbox
```

Key rule: the browser **never** sends booking content to the email function — it sends only the booking's UUID. The Edge Function loads the authoritative booking row from the database itself, so a tampered browser cannot change what the guest receives, nor the sender address.

## 3. Supabase setup

1. Create a Supabase project (Free tier is enough). Region: **South Asia (Mumbai)**.
2. Note the project URL `https://<PROJECT_REF>.supabase.co` and the **publishable (anon)** key from *Project Settings → API Keys*.
3. Put both in `assets/js/config.js`.
4. *Authentication → Providers → Email*: **disable public sign-ups** (accounts are created by an admin only) and enable "Confirm email = off" / auto-confirm, since admins create accounts directly.
5. *Authentication → URL Configuration*: Site URL = your GitHub Pages URL.

## 4. Database setup

Open *SQL Editor → New query*, paste the whole of `supabase/migrations/001_schema.sql`, run it, then do the same with `supabase/migrations/002_day_use.sql`. Together they create:

* `profiles`, `rooms`, `bookings`, `email_logs`, `settings`, `gmail_connection`, `oauth_states`, `booking_counters`
* indexes (dates, statuses, room, plus trigram indexes for search)
* **booking IDs** `INL-YYYY-00001` generated by a row-locked per-year counter inside a trigger — never by JavaScript, and never duplicated under concurrency
* **`remaining_amount`** as a generated column (`total_amount - advance_paid`)
* **double-booking protection** (see below)
* status-transition rules, audit fields (`created_by`, `checked_in_by`, …)
* `booking_type` (`OVERNIGHT` / `DAY_USE`), a per-room `day_use_price`, and hotel-wide default day-use hours in `settings`
* the demo rooms and one clearly marked demo booking

### Double-booking protection

Two layers, both in PostgreSQL, and both work down to the minute so a daycation and an overnight
stay can share a room on the same date:

1. The `bookings_guard` trigger locks the room row (`SELECT … FOR UPDATE`) and then checks for an overlapping active booking, raising
   `Room 101 is already booked for the selected dates and times.`
2. A GiST **exclusion constraint** `bookings_no_overlap` makes overlapping active bookings for the same room impossible even if a trigger were bypassed:

```sql
exclude using gist (
  room_id with =,
  tsrange(check_in_date + check_in_time, check_out_date + check_out_time, '[)') with &&
) where (booking_status in ('CONFIRMED','CHECKED-IN'))
```

`'[)'` means the moment one guest leaves is free for the next. Cancelled and checked-out bookings never block a room.

The browser also greys out rooms that are already taken, but that is only a convenience — the
database is the single authority, and it is what rejects a clashing booking.

## 4b. Day use (daycation)

A **day-use** booking is one where the guest arrives and leaves on the same day — no night stay.

**How staff create one.** On *New Booking*, switch the toggle at the top of **Stay & Room** from
*Overnight Stay* to **Day Use (Daycation)**. The check-out date disappears (it is always the same
day), the two time fields become **Arrival** and **Departure**, and they are pre-filled with the
hotel's default day-use hours. Staff can change those times for each guest.

| Setting | Where | Default |
|---|---|---|
| Default day-use hours | *Settings → Hotel Information* → **Day-use start / end time** | 12:00 PM – 6:00 PM |
| Day-use rate per room | *Rooms → edit a room* → **Day-use rate** | 0 (= not offered) |

The booking form suggests the room's day-use rate instead of the nightly rate, with a **use this**
button. If a room has no day-use rate yet, the form says so and an admin can add one in *Rooms*.

**Availability.** Because availability is time-based, all of these are handled correctly:

* an overnight guest checking out at 10:00 AM and a daycation from 12:00 PM — **both allowed**, same room, same day;
* two daycations in the same room with overlapping hours — **blocked**;
* a daycation from 7:00 PM after one that ends at 6:00 PM — **allowed**;
* a daycation in the middle of somebody's overnight stay — **blocked**.

**Everywhere else.** Day-use bookings carry a purple *Day use* marker in the dashboard, the bookings
list and the booking page; the bookings list has an **Overnight & day use** filter; the dashboard has
a **Day use today** counter; the calendar draws them as a single rounded bar with a ☀ marker; and the
confirmation email and the printed slip say *Day Use Confirmation* with **Arrival** and **Departure**
times instead of check-in/check-out dates.

## 5. RLS setup

RLS is enabled on every table by the migration; `anon` has no access at all.

| Table | ADMIN | STAFF |
|---|---|---|
| `profiles` | read all, update all | read |
| `rooms` | full | read |
| `bookings` | read/create/edit/**delete**, **cancel** | read/create/edit, check-in, check-out |
| `email_logs` | read all | read confirmation logs (writes only from Edge Functions) |
| `settings` | read/update | read |
| `gmail_connection`, `oauth_states`, `booking_counters` | no direct access (service role only) | no access |

Cancel-only-by-admin and all status transitions are enforced by the database trigger, not by hiding buttons. `email_status` can only be changed by the service role (the Edge Function), so a user cannot fake "SENT".

## 6–8. Google Cloud, Gmail API and OAuth setup

1. **Google Cloud Console → APIs & Services → Library → Gmail API → Enable** (in the project that owns the hotel Gmail).
2. **Google Auth Platform → Clients → Create client → Web application.**
3. Add **Authorised redirect URI**:
   `https://<PROJECT_REF>.supabase.co/functions/v1/gmail-oauth`
4. Copy the **Client ID** (public) and **Client secret** (private — store it only in Supabase secrets, see §10).
5. **Google Auth Platform → Audience**: while the app is in *Testing*, add the hotel Gmail address under **Test users**.
   *Note: in Testing mode Google expires refresh tokens after 7 days. For daily use, press **Publish app** (after filling the Branding page) so the connection keeps working. The app stays "unverified" — that is fine for an internal app with a handful of users; the owner just clicks "Advanced → Continue" once while connecting.*
6. Scopes requested: `https://www.googleapis.com/auth/gmail.send` plus `openid email` (only to display which account is connected). Nothing else.

## 9. Supabase Edge Functions

Deploy with the Supabase CLI:

```bash
supabase login
supabase link --project-ref <PROJECT_REF>
supabase functions deploy gmail-oauth               --no-verify-jwt
supabase functions deploy send-booking-confirmation --no-verify-jwt
supabase functions deploy admin-users               --no-verify-jwt
```

`--no-verify-jwt` is required because Google's redirect carries no Supabase token. **Every function verifies the caller's session and role itself** (`requireUser`), so this is not a security hole.

## 10. Secret configuration

GO TO: **Supabase → Project Settings → Edge Functions → Secrets → Add new secret**

| Name | Value |
|---|---|
| `GOOGLE_CLIENT_ID` | your OAuth client ID (`…apps.googleusercontent.com`) |
| `GOOGLE_CLIENT_SECRET` | **your OAuth client secret — paste it only here, never in chat, code or GitHub** |
| `GOOGLE_REDIRECT_URI` | `https://<PROJECT_REF>.supabase.co/functions/v1/gmail-oauth` |
| `APP_URL` | your GitHub Pages URL, no trailing slash |
| `ALLOWED_ORIGINS` | `https://<user>.github.io` |
| `GMAIL_ALLOWED_ACCOUNT` | the hotel Gmail address (blocks connecting a wrong account) |
| `BOOTSTRAP_ADMIN_EMAIL` | the email allowed to run the one-time first-admin setup — **delete this secret after setup** |

`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_ANON_KEY` are provided automatically by Supabase — do not add or expose them.

## 11. GitHub Pages deployment

1. Push this repository to GitHub.
2. *Settings → Pages → Build and deployment*: **Source = Deploy from a branch**, Branch = `main`, Folder = `/ (root)`.
3. The site appears at `https://<user>.github.io/<repo>/` within a minute or two.

All paths in the app are relative and routing uses the URL hash (`#/bookings`), so refreshing any page works on GitHub Pages without a 404 workaround.

## 12. Admin setup

1. Open the site. The login screen offers **"Set up the administrator account"** (it appears only while no admin exists *and* `BOOTSTRAP_ADMIN_EMAIL` is set).
2. Enter that email, your full name and a password of at least 8 characters — **you type the password yourself; it is never sent to anyone.**
3. You are signed in as ADMIN.
4. Delete the `BOOTSTRAP_ADMIN_EMAIL` secret in Supabase — first-time setup is then permanently disabled.
5. Add staff under **Settings → Staff Management** (name, email, role, temporary password). Staff can change their own password under **My Account**.

## 13. Gmail authorization

1. Sign in as ADMIN → **Settings → Gmail Integration**.
2. Click **Connect Gmail**.
3. Sign in with the hotel Gmail account and **leave the "Send email on your behalf" permission ticked**. (In Testing mode Google shows "Google hasn't verified this app" — click *Advanced → Go to … (unsafe)*; it is your own app.)
4. You are returned to Settings with **CONNECTED** and the account shown.
5. Send a **test email** to yourself to confirm.

The refresh token is stored in Supabase Vault (encrypted) and is never returned to the browser. **Disconnect** revokes it at Google and deletes it.

## 14. Testing

Sign in and check:

* Booking creation, editing, cancellation (admin only), check-in, check-out, invalid transitions
* **Double booking:** create a booking for room 501 on given dates, then try another overlapping booking for the same room → `Room 501 is already booked for the selected dates.`
* **Save Booking** → saves, sends nothing. **Save & Send Confirmation** → saves, then sends and records the result
* Failed email (e.g. Gmail disconnected) → booking stays saved, email status `FAILED`, error shown, **Resend** works and adds a new log line
* Search, filters, pagination, calendar, print, staff permissions (a STAFF account cannot cancel, delete, manage rooms/staff or see Settings), mobile layout

A ready-made concurrency check (10 simultaneous bookings for the same room, only 1 may succeed) is in `tests/concurrency_test.sh`, and `tests/db_tests.sql` exercises the RLS rules directly.

## 15. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `redirect_uri_mismatch` | The URI in Google Cloud must match `GOOGLE_REDIRECT_URI` exactly, including `https://` and no trailing slash. |
| "Gmail is not connected" | An admin must connect Gmail in Settings. |
| "Gmail authorization has expired or was revoked" | Testing-mode tokens expire after 7 days, or access was removed at myaccount.google.com/permissions → click **Reconnect Gmail** (and publish the app to stop this recurring). |
| Connection succeeds but returns `no_refresh_token` | Google only returns a refresh token on first consent — remove the app under myaccount.google.com/permissions and reconnect. |
| "Google rejected the app credentials" | `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` wrong in Supabase secrets. |
| Login says the account is inactive | The admin deactivated it, or the profile row is missing. |
| "Room X is already booked for the selected dates." | Correct behaviour — the dates overlap an active booking for that room. |
| Email status stuck on `SENDING` | The send attempt crashed mid-flight; simply resend. The history keeps both attempts. |
| Nothing loads, console shows config error | `assets/js/config.js` still has the placeholder values. |

### Data retention

Bookings are **kept forever** by default and are never deleted automatically. The `settings.retention_policy` field records the hotel's intended policy (FOREVER / 24 months / 12 months) for future use.

### Free-tier notes

No realtime subscriptions, no polling, no file uploads. The dashboard uses a single RPC for all counters, lists are paginated, and email bodies are not stored (only subject, status, recipient and any error).
